# Contributing to d-mcp

d-mcp edits configuration files that belong to users and their coding-agent harnesses. Keep changes small, tested and explicit about the behavior they change.

## Preflight

The Rust toolchain comes from `rust-toolchain.toml` (stable, with `clippy`, `rustfmt` and `llvm-tools-preview`); `rustup` installs it on first use. The extra tools (`cargo-llvm-cov`, `cargo-deny`) are pinned in `mise.toml`; install them with `mise install`.

```sh
mise run check        # cargo fmt --check, cargo clippy -D warnings, cargo test --locked
mise run check:full   # check, plus coverage threshold and cargo deny check, as in CI
```

Run `mise run check` before every commit and `mise run check:full` before opening a PR. CI additionally builds against the MSRV (`rust-version` in `Cargo.toml`) and runs tests on Linux and macOS. Keep the tool versions in `mise.toml` in sync with the `cargo install --version` pins in `.github/workflows/ci.yml`.

## Test rules

- Tests never use the network.
- Every mutation of user data has a test for its failure path (the write fails or is refused, and the existing data is left intact).
- Every mutating command has `--dry-run` coverage that proves nothing is written.
- Command-level tests live in `tests/` and build on `tests/common/mod.rs`. Every command runs with `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and the `XDG_*` directories inside a fresh temporary directory and without `D_MCP_STORE`, so no test touches the real `~/.d-mcp` or real harness configuration. Its environment otherwise starts empty (only `TMPDIR` and the `cargo llvm-cov` variables `LLVM_PROFILE_FILE` and `CARGO_LLVM_COV*` are passed on), so a variable of your shell, such as `GITHUB_TOKEN`, never changes a test's outcome; still give variables a test sets or expects unset a `DMCP_TEST_` prefix. Never bypass this helper.
- `PATH` is always controlled: by default it holds only an empty directory, because a `codex` or `claude` executable on it makes that harness count as present, and d-mcp writes Claude Code entries by running `claude`. Tests put the fakes on `PATH` with `TestEnv::with_path`; the Codex login-state tests install `tests/support/fake-codex.sh` as `codex` in a controlled `PATH` directory. The fake records its calls in `$CODEX_HOME/fake-codex.log` (and the working directory of each in `fake-codex-cwd.log`), takes its behavior from `$CODEX_HOME/fake-codex-mode`, answers `--version` for the `doctor` tests (`version-mismatch` and `version-garbage` modes print an unverified version and canary text) and `mcp list --json` (the only other call d-mcp makes), and prints canary strings, also on stderr, that must never reach d-mcp's output or store. Like the fake `claude`, it refuses to run (exit 97) unless `$CODEX_HOME` lies, one or two levels down, in a directory in the system temp directory marked with `.d-mcp-test-root`. Because that `PATH` holds only the fake, it uses shell builtins only and calls `sleep` by absolute path; keep it that way. Timing assertions use generous bounds for slow CI machines.
- The Claude Code tests use the fake `claude` in `tests/support/fake_claude.rs`, a Rust test target without the libtest harness (`[[test]] harness = false` in `Cargo.toml`, so `cargo install` never installs it). `TestEnv::fake_claude_dir` copies the built fake into a temporary `PATH` directory. It edits only `mcpServers` of the Claude Code configuration file in the test's `CLAUDE_CONFIG_DIR` (or `HOME`), and like Claude Code copies an existing file to `<configuration home>/backups/` before each write (with an empty `CLAUDE_CONFIG_DIR`, the configuration home is its working directory). It normalizes entries like Claude Code, logs every call to `<root>/fake-claude.log` (arguments, working directory, `PATH`, `HOME`, `CLAUDE_CONFIG_DIR`, `DISABLE_AUTOUPDATER` and whether `MCP_CLIENT_SECRET` is present, never its value), takes failure, timeout, concurrent-edit, login and `version` directives from `<root>/fake-claude-mode` (`TestEnv::claude_mode`), and prints canary strings, also on stderr. It refuses to run unless its `HOME` lies in a temporary directory marked with `.d-mcp-test-root`, which `TestEnv::new` creates. A run filtered with `--test sync_claude` also needs `--test fake_claude`, so that the fake is built. `fake_claude_binary` in `tests/common/mod.rs` finds the build next to the running test executable (`target/<profile>/deps/`, also under `cargo llvm-cov`'s own target directory, on Linux and macOS) and never uses a stale one: a `fake_claude-<hash>` counts only when it is at least as new as every source in its rustc dep-info file `fake_claude-<hash>.d` (the fake, the fixtures it includes and `Cargo.toml`), the same freshness rule cargo applies. Without a fresh build the test panics and names the command that builds it.
- Git-source tests use `TestEnv::with_git()`: `PATH` then holds only a symlink to the resolved `git` binary, and git's configuration is isolated (`GIT_CONFIG_GLOBAL` points to a file in the temporary root, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` unset). Remotes are local bare repositories built with `TestEnv::remote` under their own isolated configuration; no test clones over the network. To sync to Claude Code as well, put `TestEnv::git_bin()` and the fake's directory on `PATH` with `TestEnv::with_path`. A second machine is a second `TestEnv` with its own store and harness homes that clones the first one's bare repository by path (`tests/two_machines.rs`). The unit tests of `src/git.rs` run the system `git` with the same isolation and are skipped without one.
- Claude Code fixtures live in `tests/fixtures/claude/`: configuration files with account and cache canaries, and the recorded `claude mcp get` outputs in `get/`. Override fixtures for the Claude Code allow-list live in `tests/fixtures/claude-overrides/` and follow the same `valid/` and `invalid/<rule-code>/` layout as `tests/fixtures/codex-overrides/`.
- The discovery, inventory, adoption, status, doctor and uninstall tests share the combined fixture `tests/fixtures/real-setup/` (Codex and Claude Code user files, a repository with `.mcp.json` and `.codex/config.toml` layers, local definitions and a team source). `TestEnv::install_real_setup` copies it into the isolated environment, substitutes `@REPO@` and `@CWD@`, and creates the repository's `.git`; `TestEnv::cmd_in`, `json_in` and `text_in` run commands from its working directory. Its canaries start with `CANARY`.
- Every command that renders harness entry content must go through `src/redact.rs`, and `tests/redaction.rs` must run it in text and JSON form against the canary fixture: no canary may reach stdout, stderr or a store file. The two forms run in twin environments from the same fixture, so a command that writes succeeds in both forms; give each command its expected exit code. A new command or output position needs a case there.
- Tests never run the real `claude` either. When you verify Claude Code behavior by hand, export both `HOME` and `CLAUDE_CONFIG_DIR` to a fresh temporary directory in the same shell command, and run it from a fresh temporary working directory, so your own `~/.claude.json` and `~/.claude/` (which a running Claude Code session owns) are never touched.
- Tests never run the real `codex`. When you verify Codex behavior by hand, export `HOME` and `CODEX_HOME` to a fresh temporary directory in the same shell command, so your own `~/.codex` is never touched. `tests/fixtures/codex-rewrite/` holds a file d-mcp wrote and the same file after the real Codex re-saved it; recapture both this way when the rendering or the verified Codex version changes.
- Codex config fixtures live in `tests/fixtures/codex/` and must stay byte-exact: `crlf.toml` and `trailing-comments-crlf.toml` hold CRLF line endings and `no-trailing-newline.toml` has no final newline, so do not let an editor normalize them; `tests/fixtures/codex/.gitattributes` marks them `-text` so Git keeps their bytes.
- Override fixtures for the Codex allow-list live in `tests/fixtures/codex-overrides/`; a file in `invalid/<rule-code>/` (`override-key`, `override-type`, `override-transport`) must fail with exactly that rule code, a file in `valid/` must pass.
- Launcher audit fixtures live in `tests/fixtures/launchers/`: every definition in `pinned/` must have no finding, every one in `unpinned/<rule-id>/` exactly one finding of that rule. Every runner of the audit table needs a pinned and an unpinned fixture (a unit test in `src/audit/tests.rs` checks both).
- Definition fixtures live in `tests/fixtures/definitions/`. A file in `invalid/<rule-code>/` must fail with exactly that rule code; a file in `valid/` must pass. The file stem is the server name. A new rule code needs a fixture and an entry in the rule-code table of `docs/reference.md`.
- The error-code table in `docs/reference.md` (between the `error-codes` markers) is parsed by a unit test; keep every error code and its exit code in sync with `src/error.rs`.
- The coverage threshold lives in `coverage-threshold` (percent of lines). It may be raised but never lowered.

## Dependencies

`cargo deny check` enforces the policy in `deny.toml`: allowed licenses, no yanked crates, no wildcard versions, crates.io only. Add exceptions only when unavoidable, keep them narrow (one crate or advisory) and comment why.

## Schema rule

Until 1.0.0, persisted schemas stay at version 1 and fields are added without migration. From 1.0.0 on, every schema change bumps the version and ships a migration.

## Commits and pull requests

- Use Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:` ...), in English.
- PRs are squash-merged, so the PR title becomes the commit subject; the `pr-title` workflow checks it.
- Pin every GitHub Action by full commit SHA, with the version in a trailing comment.
